# 局部源码 harness

适用于修改范围集中、职责明确且依赖可可靠保留或隔离的模块；完整构建昂贵不是必要条件。

## 先确定边界

- 找到真实模块、头文件、依赖、编译宏与必要链接库。不要编译所有 `.c` 来碰运气。
- 选稳定的 API/模块边界；考虑候选可能拆分文件，避免把现有文件布局误当行为契约。
- 依赖不明、关键行为受整体初始化/链接影响时，扩大到相关构建目标或复用现有测试。

## 保留源码

- 将辅助入口、输入数据、必要包装构建文件登记为 `materials`，放在 `build/verification/`。
- BuildWorkflow 编译辅助入口加当前 worktree 的真实 `.c` 文件；包含项目真实头文件。
  不修改原源码、头文件或根 `CMakeLists.txt`。
- 必须测试内部 static 函数时，可以让辅助翻译单元 include 当前侧的真实源码，保持材料一致；
  这会依赖源码组织，需要解释为何该边界适合本次任务。不得复制函数正文。
- 允许隔离与修改无关的环境依赖，但不能替换被修改的实现，不能使用返回固定成功的桩。
  说明隔离掉了哪些集成行为。
- 独立包装 `CMakeLists.txt` 也属于材料，在构建目录下调用它，不改项目构建定义。

## 有效验证

BuildWorkflow 在每侧编译，检查 status/exitCode 并断言产物存在。
TestWorkflow 运行产物，先确认用例执行和退出符合预期，再声明真实行为观测。
材料固定后不可按侧修改，也不能在 TestWorkflow 中重新编译或改写 helper。

局部验证保护选定模块的行为。它不能自动证明整个产物能构建、最终链接成功或完整应用的集成行为。
