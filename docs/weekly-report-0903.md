# 本周工作汇报（2026-08-31 ~ 09-03）

这周核心是把「AI 自动生成 workflow、驱动构建和测试来做行为保持验证」这条链路真正跑通。整体分三个阶段：先解决 workflow 没被真正使用的问题，再做了一次结构性的重构，最后花大力气把端到端跑通——这中间排查了一个很有意思的性能问题。

## 第一阶段：让 workflow 真正驱动流程

之前设计了一套 TypeScript workflow 的抽象，让 AI 生成构建和测试脚本。但做着做着发现一个问题：这套东西实际上没被真正使用，验证走的是内置的固定逻辑，workflow 更像一个摆设。所以第一步是把执行架构改成 workflow-driven：workflow 真正接管构建和测试的执行，产出可延迟声明的结果，并且引入 plan API 让 AI 能分步规划。同时把测试 workflow 改成自驱动模式——它自己声明期望的行为结果，宿主负责在两版代码（重构前/后）上各跑一遍再做差分对比，而不是靠人肉写死断言。这一阶段把「AI 生成 workflow」的雏形真正落地了。

## 第二阶段：结构调整，把 build 做成 test 的子能力

跑了一次真实的 libuv 重构 e2e 之后，暴露了结构问题：测试的编写者不知道构建产物在哪，只能自己重新构建一份来测——白花十来分钟，而且测的还不是宿主验证的那份；构建和测试被强制拆开，测试方完全被动，只能用别人塞给它的产物，产物怎么传递也成了问题。

后来想明白一个点：**build 本质上是为 test 提供产物的，而写 test 的人最清楚自己要什么**。于是把流程改造成 subagent 协作：test-writer 在会话里按需派出 build-writer 子 agent，build-writer 专注产出构建 workflow 并向 test-writer 汇报产物路径和用法；test-writer 显式声明它依赖哪些构建，宿主在执行测试前把声明的构建全部跑掉。这样产物知识由 AI 之间自然传递，宿主不再需要理解产物，还天然支持多构建，声明也成了可审计的线索。老的 chooser/生成路径整个删掉，架构干净了很多。

## 第三阶段：改完了却跑不通——先做可观测性，再查一个反直觉的慢

重构完成、单测都过了，但真实 e2e 死活跑不完——一个小到不能再小的 C demo，配一个平时每秒 100+ token 的模型，一次 e2e 却要二三十分钟。最初完全无法定位，因为 workflow-session 内部对模型轮次、子 agent 启停、工具调用完全没有日志，早期甚至 311 条日志全是心跳。于是先做了可观测性改造：引入级别化日志库、把完整会话镜像落盘，让内部过程变得可见。

然后用日志逐段排查，排除了模型和网关的嫌疑（请求列表显示模型每轮只要几秒），最后定位到真正的慢因：**宿主的安全 scope 白名单和 Glob 的根目录递归互相冲突，AI 的探索操作反复被拒，陷入猜路径的死循环**——单个子 agent 能白白消耗二十多次无效拒绝。修掉这个之后，又顺着日志钉死了十几个真问题：比如子 agent 缺写工具、glob 误拒、对源码做 JSON 解析崩溃、构建产物执行路径被宿主拒绝等等，大多是声明制新架构带来的边界问题。

最后一轮，验证段成功跑通：重构前后两侧构建都通过，10 项行为期望全部一致，流程走到了 ACCEPTED——这是声明制全链路第一次完整跑通。

## 遗留事项

- e2e 现在靠一个临时开关绕过了 scope 校验来验证假设，后续要把安全边界重新设计收紧；
- 流程缺中断恢复机制：这次失败在验证段时不得不重跑全部 AI 阶段，打算做成可恢复的。
