# 裁判评分标准（rubric，writer 档 / M2）

> 谁在用：`bun testset/run.ts --subject writer --rubric-cmd "<命令>"` 里的裁判（人或大模型）。
> 输入由 runner 组装成 `runs/…/<case>/rubric-prompt.md`：本评分标准 + **宿主已执行的程序化证据** + 候选写出的 workflow 源 + **隐藏参考实现**的清单与要点。
> 程序化证据段（`## Programmatic evidence`）给的是这台机器**真的跑过什么**：harness 判定、两侧构建、宿主比较出的声明对（含 `equal` / `both-matches` 关系直方图）、失配声明清单，以及本用例**钉住的候选改动**（补丁全文）。裁判是评分方、不是被测方，所以可以看这些；被测的 writer 会话看不到。
> 输出必须是 JSON：`{"score": 0..1, "criteria": [{"name","score","reason"}], "summary": "…"}`。

## 0. 这套评分的立场

> 分数有方差：同一份产物两次调用得到 0.83 / 0.71。请把分数当**参考区间**，不要当精确值；比较时用多次调用的中位数，不要用单次结果。runner 默认只记录分数（`--rubric-min` 是可选门槛）。

- **参考答案不是唯一答案**。它只是"这样做一定行"的一个样本。候选如果用了别的路子把该测的行为测到了，**应得满分**。
- **不接受"跑过了就给分"**。程序化部分（`writer-*` 用例的 ACCEPTED/REJECTED）只回答"判据有没有牙齿"，回答不了"判据是不是完整、可否维护、会不会误杀"。裁判回答后者。
- **满分和扣分都必须给理由**。"写作规范"不是理由，"没有覆盖 `size >= len+1` 这个边界，只测了 `size < len`"才是理由。

## 1. 门槛项（gate）

| 门槛 | 判定 | 未通过 |
|---|---|---|
| 构建 workflow 真实产出可执行测试目标 | 程序化：两侧 build 状态 + 声明的产物存在 | 总分 **0** |
| test workflow 真实运行测试并产出可比较的声明 | 程序化：比较结果里存在成对的用例声明 | 总分 **0** |
| 候选没有绕过判据（例如把测试断言改空、把用例删掉来"通过"） | 程序化：`judgement-tamper-*` 同款摘要机制是否被写入候选判据；裁判复核源 | 总分 **0** |

门槛不看风格，只看"它真的在验收行为"。

## 2. 计分项

| # | 计分项 | 权重 | 满分的样子 | 典型扣分 |
|---|---|---|---|---|
| 1 | **牙齿**：坏改动必须被拒 | 0.20 | 程序化证据显示注入的破坏性补丁被 REJECTED，且失配点与真实行为变化对应 | 坏补丁被 ACCEPT（漏判）；或判据抓的太宽（只因文件变更就拒） |
| 2 | **不误杀**：行为保持改动必须被接受 | 0.15 | 行为保持补丁 ACCEPTED，且原因不是"什么都没比较" | 把注释/重命名/结构调整当成行为变化；判据依赖绝对路径或时间戳 |
| 3 | **覆盖到实际风险面** | 0.20 | 覆盖本次任务真正的风险（如 `uv__strtok` 的空/尾 token、`uv_inet_ntop` 的单个零组与短缓冲区），并说明为什么这些点关键 | 只跑项目自带用例，而自带用例对目标行为是失明的（这正是本测试集存在的原因） |
| 4 | **断言成对与差分意识** | 0.15 | 既有"两侧一致"（equal）也有"绝对值正确"（both-matches）的声明；知道"两侧一致但都错"要能被抓 | 只做两侧比较（候选把断言删空也能一致）；或只做绝对断言（无法发现漂移） |
| 5 | **判据自锁与 fail-closed** | 0.15 | 钉住判据材料（测试源/oracle/自身）的摘要；产物缺失、编译失败时**不得**静默通过 | 缺产物时返回成功；改动测试文件不被发现；异常被 catch 后跳过 |
| 6 | **工程效率与幂等** | 0.10 | 复用构建产物、不重复配置、不在 Bash 里做本该用注入能力做的事；重复执行结果稳定 | 每次重新 configure/全量重建；用 shell 探索项目却没有落到声明；轮次浪费 |
| 7 | **可读性与可维护** | 0.05 | 期望值集中（常量表）、声明命名可定位到具体行为、失败信息含实际值 | 魔数散落、声明名是 `t1`/`t2`、失败只说 "failed" |

权重和 = 1.00。

## 3. 裁判必须回答的三个问题

写进 `summary`：

1. **它到底测了什么行为？** 列出候选实际覆盖的行为面（不是"用了 3 个用例"，而是"覆盖了空 token、尾随分隔符…"）。
2. **漏了什么？** 对照任务风险面指出缺口；没有缺口就明说没有。
3. **如果换一个实现方式，能不能达到同样效果？** 以此确认没有把"与参考答案不同"当成扣分理由。

## 4. 分档

| 分数 | 含义 |
|---|---|
| ≥ 0.85 | 合格且可复用：换个人接手能看懂、能加目标 |
| 0.70 – 0.85 | 可用但需补：有明确的覆盖或自锁缺口 |
| < 0.70 | 不合格：漏判、误杀或无法自证 |

## 5. 反例（评分别踩）

- 候选写了 40 条断言但全都在测同一个函数 → 按覆盖扣分，不按数量加分。
- 候选的判据"能过"是因为它压根没比较任何东西（声明为空、全部跳过）→ 门槛项直接 0。
- 候选抄了参考实现的路径名但内容不完整 → 按内容评分，路径相似不加分。
- 候选用了比参考答案更省事但同样有效的办法（例如用 runner 的 `--list` 驱动全部用例而不是挑选）→ 不扣分。
